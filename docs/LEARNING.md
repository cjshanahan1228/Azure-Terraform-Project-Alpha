# Learning path

This repo is a sandbox for learning Terraform on Azure properly. Work through the
stages in order; each one builds on the last. Every stage has **goals**,
**exercises** and a **done when** line so you know when to move on.

> Ground rules: branch per exercise (`feat/…`, `docs/…`), open a PR that closes an
> issue, let CI run, and only `terraform apply` against **dev** — after reading the plan.
> Run `terraform destroy -var-file=environments/dev/dev.tfvars` when you're done for the day.

---

## 1. Plain resources

**Goals**
- Understand the core loop: `init` → `plan` → `apply` → `destroy`.
- Read a plan: `+` create, `~` update in place, `-/+` replace, `-` destroy.
- Know the difference between arguments, attributes, and references (`azurerm_resource_group.this.name`).

**Exercises**
1. In a scratch folder, write a single `azurerm_resource_group` and a `azurerm_storage_account` with no modules.
2. Change a tag and see an in-place update; change the storage account `name` and see a replacement.
3. Add an `output` and read it with `terraform output`.

**Done when** you can predict, before running `plan`, whether a change will update in place or replace.

---

## 2. Modules

**Goals**
- Understand root vs child modules, inputs (`variables.tf`), outputs (`outputs.tf`) and `source`.
- See how this repo's root `main.tf` wires `modules/networking`, `storage`, `app` and `secrets`.

**Exercises**
1. Trace one value end to end: `environments/dev/dev.tfvars` → `variables.tf` → `main.tf` → `modules/storage/variables.tf` → resource.
2. Add a new input to `modules/storage` (e.g. `access_tier`) with a default, and pass it from the root.
3. Expose a new module output and surface it in the root `outputs.tf`.
4. Make a module optional with `count` the way `module "app"` is, and handle it with `one(module.app[*]...)`.

**Done when** you can add a module input/output without breaking `terraform validate`, and explain why `module.app` needs `[0]` or `[*]`.

---

## 3. `for_each` and `dynamic` blocks

**Goals**
- Know when to use `count` (a number of identical things, or an on/off toggle) vs `for_each` (things with identities).
- Generate nested blocks with `dynamic`.

**Exercises**
1. Add a third subnet to `subnets` in `dev.tfvars` and confirm the plan only adds one resource.
2. Remove a subnet from the middle of the map — compare with what `count` would have done.
3. Add an NSG to `modules/networking` with `security_rule` blocks generated by `dynamic "security_rule"` from a list of objects.
4. Use a `for` expression to build an output map (see `subnet_ids`).

**Done when** you can add or remove an item from a collection and the plan touches only that item.

---

## 4. Replace workflows: `-replace`, `moved` and `import` blocks

**Goals**
- Force recreation safely, and refactor code without destroying real infrastructure.

**Exercises**
1. `terraform plan -replace='module.app[0].azurerm_linux_web_app.this'` — read what would be recreated.
2. Rename a resource (e.g. `azurerm_subnet.this` → `azurerm_subnet.subnet`) and add a `moved {}` block so the plan shows no destroy.
3. Create a resource by hand in the portal, then bring it under management with an `import {}` block and `terraform plan -generate-config-out=generated.tf`.
4. Remove something from Terraform without deleting it, using a `removed {}` block (Terraform 1.7+).

**Done when** you can rename or move a resource and the plan shows zero destroys.

---

## 5. Policy-as-code: Azure Policy, OPA, Checkov, tflint

**Goals**
- Catch mistakes before `apply` (lint, security scan) and enforce rules in Azure itself (Azure Policy).

**Exercises**
1. Run `tflint --init && tflint --recursive` with the `azurerm` ruleset; fix what it finds.
2. Run `checkov -d .` and decide which findings to fix vs suppress with a justified `#checkov:skip=` comment.
3. Write an OPA/Conftest rule over `terraform show -json plan.out` that rejects resources missing a `project` tag.
4. Assign a built-in Azure Policy (e.g. "Require a tag on resources") to the dev resource group with `azurerm_resource_group_policy_assignment`.
5. Add tflint and Checkov as CI steps (pinned by SHA).

**Done when** CI fails on a PR that removes the required tags, and passes once they're back.

---

## 6. State deep dive

**Goals**
- Understand what state is, why it's remote, how locking works, and how to repair it.

**Exercises**
1. Bootstrap the dev state storage account (Entra-only auth, versioning, soft delete), fill in `environments/dev/backend.hcl`, and `terraform init -backend-config=environments/dev/backend.hcl`.
2. Start a `plan` in two terminals at once and see the blob lease lock; learn when (not) to use `terraform force-unlock`.
3. `terraform state list` / `state show`; then `terraform state mv` a resource and compare with a `moved` block.
4. `terraform state rm` a resource, then bring it back with `terraform import` (CLI) or an `import {}` block.
5. Read another stack's outputs with `data "terraform_remote_state"` and discuss why outputs/data sources are often better.

**Done when** you can recover from a lost resource-to-state mapping without deleting anything in Azure.

---

## Interview checkpoints

- What happens if two people `apply` at once without locking?
- `count` vs `for_each` — when does `count` bite you?
- How do you rename a resource without downtime?
- Why use `use_azuread_auth` and OIDC instead of storage keys and client secrets?
